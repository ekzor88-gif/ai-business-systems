# План Миграции Данных (Migration Plan)

В данном документе описывается стратегия перехода со старого формата `knowledge.json` на новую структуру **Инженерного графа знаний (Engineering Knowledge Graph)**.

---

## 1. Что меняется в архитектуре хранения

| Старая концепция | Новая концепция (Редизайн) | Тип изменений |
| :--- | :--- | :--- |
| Данные хранятся в плоском JSON `knowledge.json` | Данные разделены на слои `storage/raw/`, `storage/normalized/`, `storage/knowledge/` | Структурный |
| Проекты описаны внутри `raw_resume_data.work_experience` | Выделена независимая сущность `Project` на верхнем уровне | Логический |
| Технологии вложены в плоский список строк `skills` | Разделено на сущности `Skill` (оценка) и `Technology` (каталог) | Кардинальный |
| Достижения содержат плоские строки `metric` и `value` | Числовые метрики вынесены в самостоятельную сущность `Metric` | Типизированный |
| Нет подтверждения утверждений резюме | Внедрены доказательства `Evidence` (ссылки на строки кода, коммиты) | Прослеживаемый |
| Уроки и Архитектурные решения не фиксировались | Внедрены сущности `Lesson` и `Decision` | Инженерный |

---

## 2. Какие JSON-файлы изменяются

1.  **`knowledge.json`**:
    *   **Удалено**: поле `raw_resume_data` больше не хранится в итоговом графе знаний (перенесено в `storage/raw/`).
    *   **Добавлено**: массивы объектов `skills` (структурированные), `projects`, `technologies`, `metrics`, `evidence`, `lessons_learned`, `decisions` на верхнем уровне.
2.  **`project.json`** / **`portfolio.json`**:
    *   **Добавлено**: поддержка ссылок на новые сущности `metrics`, `evidence`, `lessons_learned` и `decisions` внутри объектов описания проектов и достижений.

---

## 3. Схема Преобразования Данных (Mapping & Migration Rules)

Для миграции старого JSON без потери информации применяется следующий алгоритм отображения полей:

### 3.1. Преобразование Навыков (Skills -> Technology & Skill)
Для каждой строки из старого массива `skills` (например, `["Python", "n8n"]`):
1.  Создается запись в глобальном реестре `Technology`:
    ```json
    { "id": "python", "name": "Python", "category": "Language" }
    ```
2.  Создается объект `Skill` на верхнем уровне:
    ```json
    {
      "id": "python",
      "name": "Python",
      "category": "Language",
      "level": "Intermediate",
      "confidence": 0.5,
      "verification_status": "unverified",
      "projects": [],
      "evidence": ["ev_legacy_resume"]
    }
    ```

### 3.2. Выделение Проектов (Work Experience -> Project & Experience)
Для каждого места работы в `work_experience` сканируется поле описания и выделяются проекты:
1.  Создается объект `Project` на верхнем уровне с уникальным ID (например, `proj_saas_ai_assistant`).
2.  Текстовые описания обязанностей преобразуются в массив объектов `Fact` с привязкой к созданному `Project`.
3.  В сущности `Experience` для места работы сохраняется только ссылка:
    `"projects": ["proj_saas_ai_assistant"]`.

### 3.3. Разбор Метрик (Flat Metric -> Metric Entity)
Старые текстовые достижения с плоскими метриками (например, `metric: "Time", value: "90 min to 1 min"`) парсятся:
1.  Создается объект `Metric`:
    ```json
    {
      "id": "metric_n8n_time",
      "metric_type": "Time Reduction",
      "before": "90",
      "after": "1",
      "unit": "minutes",
      "improvement_percent": 98.8,
      "confidence": 0.85
    }
    ```
2.  Объект `Fact` ссылается на созданную метрику через `"metrics": ["metric_n8n_time"]`.

### 3.4. Инициализация Доказательств (Evidence)
Для всех мигрированных фактов, проектов и навыков, не имеющих прямой ссылки на код репозитория:
1.  Создается единый объект `Evidence` с типом `docx_document` (указывающий на загруженное пользователем резюме):
    ```json
    {
      "id": "ev_legacy_resume",
      "type": "docx_document",
      "source": "input/CV.docx",
      "location": "CV.docx",
      "description": "Первоначальное резюме кандидата",
      "confidence": 0.85
    }
    ```
2.  Все сущности получают ребро `backed_by: ["ev_legacy_resume"]` и начальный `confidence: 0.85`.

---

## 4. Обратная Совместимость (Compatibility)

Для предотвращения сбоев в работе существующих пайплайнов и обеспечения мягкой миграции:
1.  **Парсинг Context Manager**: Логика парсинга в Context Manager адаптирована. Метод слияния `merge_knowledge_data` сохраняет плоские массивы `raw_resume_data.skills` для старых схем, но одновременно генерирует структурированные списки на верхнем уровне.
2.  **JSON Схемы**: Обновленные схемы в папке `schemas/` используют директивы `oneOf` и необязательные свойства, что позволяет им успешно проходить валидацию как при подаче старого плоского формата, так и нового графа.
