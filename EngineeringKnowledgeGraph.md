# Инженерный Граф Знаний (Engineering Knowledge Graph Specification)

Этот документ содержит полную архитектурную спецификацию **Инженерной базы знаний (Engineering Knowledge Base)** платформы **Portfolio Factory**. Она спроектирована как единый семантический граф знаний (Single Source of Truth) для генерации портфолио-сайтов, файлов README.md, резюме и контента для RAG-помощников.

---

## 1. Многоуровневое Хранилище Данных (Storage Layers)

Для изоляции сырых данных от семантических связей, хранилище делится на три слоя в каталоге `storage/`:

```
storage/
├── raw/            # Исходные файлы пользователя без модификаций (DOCX, PDF, txt)
├── normalized/     # Очищенные от шума структурированные JSON-слепки отдельных файлов
└── knowledge/      # Финальный связанный граф знаний (knowledge.json)
```

### 1.1. Сырой слой (`storage/raw/`)
*   **Ответственность**: Сохранение неизмененных первоисточников.
*   **Правило**: Файлы записываются один раз (например, при загрузке `resume.pdf` или выгрузке `git log`) и служат основой для последующего аудита и выявления галлюцинаций.

### 1.2. Нормализованный слой (`storage/normalized/`)
*   **Ответственность**: Структурирование данных из сырого слоя без выстраивания сложных перекрестных связей.
*   **Пример**: Распарсенное резюме приводится к схеме `resume.schema.json`, где все даты форматируются как `YYYY-MM`.

### 1.3. Слой знаний (`storage/knowledge/`)
*   **Ответственность**: Построение семантического графа, дедупликация, слияние сущностей и выявление противоречий.
*   **Правило**: Именно этот слой содержит файл `knowledge.json`, валидируемый по `knowledge.schema.json`, и питает генеративные пайплайны.

## 2. Спецификации Вершин Графа (Сущностей)

Каждая вершина в графе представлена самостоятельным JSON-объектом в плоском массиве соответствующего типа в `knowledge.json`.

### 2.1. Сущность: Project (Проект)
Выделена из мест работы в независимую сущность для поддержки сложных связей (субподряды, сторонние репозитории, открытый исходный код).
*   `id`: Уникальный строковый хэш проекта (например, `proj_mediacube_sync`).
*   `name`: Понятное наименование проекта.
*   `description`: Техническое описание архитектурного назначения проекта.
*   `project_type`: Категория (`commercial`, `pet_project`, `open_source`).
*   `status`: Состояние проекта (`production`, `maintenance`, `archived`).
*   `start_date` / `end_date`: Период участия инженера в проекте (`YYYY-MM`).
*   `technologies`: Массив ID связанных технологий.
*   `architecture`: Сведения о паттернах (`pattern`) и код Mermaid-схемы (`diagram_mermaid`).
*   `lessons_learned`: Массив ID уроков, извлеченных из проекта.
*   `repositories`: Массив ID связанных Git-репозиториев.
*   `facts`: Массив ID подтвержденных достижений инженера в проекте.
*   `metrics`: Массив ID количественных метрик улучшения.
*   `evidence`: Массив ID свидетельств (коммиты, файлы кода).

---

### 2.2. Сущность: Skill (Оценка Владения)
Описывает реальный опыт кандидата во владении конкретной технологией.

#### Описание полей и их назначение:
*   `id`: Системный ID (совпадает с ID соответствующей технологии).
*   `name`: Отображаемое имя навыка.
*   `category`: Группа (например, `Backend`, `Database`, `DevOps`). Нужна для группировки в резюме.
*   `subcategory`: Тонкая классификация (например, `ORM` для SQLAlchemy, `VectorDB` для pgvector).
*   `description`: Описание глубины понимания технологии кандидатом.
*   `level`: Текущий уровень владения (`Expert`, `Advanced`, `Intermediate`, `Beginner`).
*   `first_used` / `last_used`: Даты начала и окончания реального использования.
*   `projects`: Массив ID проектов кандидатов с этой технологией.
*   `experience`: Массив ID мест работы, где применялась технология.
*   `repositories`: Массив ID репозиториев, где присутствует код на этой технологии.
*   `facts`: Массив ID достижений инженера, где применялся этот навык.
*   `evidence`: Ссылки на прямые доказательства владения.
*   `years_of_usage`: Вычисляемое или заявленное количество лет стажа работы с инструментом.
*   `confidence`: Итоговый коэффициент достоверности навыка.
*   `verification_status`: Статус проверки (`verified` — подтвержден исходным кодом, `unverified` — только заявлен в резюме).

---

### 2.3. Сущность: Fact (Инженерный факт / Достижение)
Описывает единичное атомарное достижение разработчика.
*   `id`: Уникальный ID факта (например, `fact_mediacube_etl_synchronization`).
*   `title`: Краткое техническое название достижения.
*   `summary`: Саммари достижения в одно предложение.
*   `description`: Детальное описание по методологии XYZ.
*   `project_id`: ID связанного проекта.
*   `experience_id`: ID места работы.
*   `repository_id`: ID репозитория Git.
*   `technologies`: Массив ID задействованных технологий.
*   `metrics`: Массив ID ассоциированных количественных метрик.
*   `evidence`: Массив ID доказательств (коммиты, строки кода).
*   `lessons`: Массив ID извлеченных уроков.
*   `confidence`: Оценка достоверности факта.
*   `tags`: Теги для семантической группировки (`performance`, `etl`, `automation`).
*   `created_at` / `updated_at`: Временные штампы создания и обновления.

---

### 2.4. Сущность: Technology (Технология)
Технологии вынесены из Skills в отдельный справочник для поддержки независимых метаданных.
*   `id`: Уникальный ID инструмента (например, `postgresql`).
*   `name`: Официальное название (например, `PostgreSQL`).
*   `category`: Тип инструмента (`Database`, `Language`, `Framework`).
*   `vendor`: Компания или сообщество-разработчик (например, `PostgreSQL Global Development Group`, `Google`).
*   `documentation_url`: Ссылка на официальную техническую документацию.
*   `projects` / `facts` / `repositories`: Обратные ссылки на сущности графа знаний кандидата.

---

### 2.5. Сущность: Repository (Репозиторий)
Описывает характеристики кодовой базы на GitHub.
*   `id`: Уникальный ID репозитория (обычно название репозитория).
*   `name`: Имя репозитория на GitHub.
*   `url`: URL-адрес репозитория.
*   `description`: Описание репозитория.
*   `language`: Основной язык программирования.
*   `frameworks`: Массив обнаруженных фреймворков (например, Django, React).
*   `topics`: Теги репозитория на GitHub.
*   `projects` / `facts`: Связанные сущности графа.
*   `readme`: Содержимое или путь к файлу README.md.
*   `license`: Лицензия проекта (например, MIT).
*   `visibility`: Видимость репозитория (`public`, `private`).

---

### 2.6. Сущность: Metric (Метрика)
Изолированная количественная оценка эффективности работы инженера.
*   `id`: Уникальный ID метрики (например, `metric_mediacube_time_reduction`).
*   `metric_type`: Категория (`Performance Improvement`, `Cost Reduction`, `Scale Expansion`, `Time Reduction`).
*   `before`: Показатель до изменений (строка для поддержки разных форматов).
*   `after`: Показатель после изменений.
*   `unit`: Единица измерения (`minutes`, `RPS`, `USD/month`).
*   `improvement_percent`: Вычисленный процент улучшения.
*   `confidence`: Коэффициент уверенности в метрике.
*   `project_id` / `fact_id`: Связанный проект и факт достижения.

---

### 2.7. Сущность: Lesson Learned (Извлеченный урок)
Инженерные выводы, сделанные в ходе проектирования или оптимизации систем.
*   `id`: Уникальный ID урока.
*   `title`: Краткое название проблемы.
*   `description`: Подробное описание извлеченного урока.
*   `category`: Область (`Architecture`, `Performance`, `Process`, `Security`).
*   `project`: ID связанного проекта.
*   `technologies`: Массив ID технологий, с которыми связан урок.
*   `tags`: Ключевые слова для поиска (`idempotency`, `rate-limit`, `debugging`).
*   `confidence`: Оценка достоверности извлечения.

---

### 2.8. Сущность: Decision (Архитектурное решение)
Фиксация принятых архитектурных компромиссов (ADR в рамках графа).
*   `id`: Уникальный ID решения (например, `dec_n8n_for_integration`).
*   `problem`: Описание проблемы, стоявшей перед разработчиком.
*   `options`: Список рассматриваемых альтернатив с описанием.
*   `selected_option`: Выбранная альтернатива.
*   `reason`: Обоснование выбора выбранного решения.
*   `tradeoffs`: Компромиссы, на которые пришлось пойти.
*   `consequences`: Последствия решения для системы и процессов.
*   `project_id`: ID связанного проекта.
*   `technologies`: Массив ID задействованных технологий.

---

### 2.9. Сущность: Evidence (Доказательство)
Связывает граф семантики с физическими подтверждениями опыта.
*   `id`: Уникальный ID свидетельства (например, `ev_sync_py_code`).
*   `type`: Формат (`code_file`, `git_commit`, `pdf_document`, `docx_document`, `screenshot`, `certificate`, `video`).
*   `source`: Ссылка на репозиторий или локальный файл.
*   `location`: Указание точного расположения (номера строк `src/sync.py#L40-L115`, хэш коммита, таймкод видео).
*   `description`: Описание того, что именно подтверждает данное свидетельство.
*   `confidence`: Вес достоверности свидетельства.

---

## 3. Достоверность Знаний (Confidence Scoring Model)

Каждому объекту в графе присваивается показатель достоверности (`confidence`) на основе типа источника доказательства.

### 3.1. Базовые веса достоверности источников
| Источник (`Evidence.type` / `source`) | Вес достоверности | Обоснование |
| :--- | :--- | :--- |
| **`code_file`** | **1.0** | Исходный код написан инженером и физически существует в Git |
| **`git_commit`** | **0.95** | Коммит с подтвержденным авторством в репозитории GitHub |
| **`certificate`** | **0.90** | Внешний подтвержденный документ от облачного провайдера/школы |
| **`docx_document` / `pdf_document`** | **0.85** | Резюме, предоставленное кандидатом (декларативный опыт) |
| **`document`** | **0.75** | Внутреннее техническое задание или архитектурное описание |
| **`conversation`** | **0.60** | Сведения, извлеченные из текстового чата или интервью |
| **`assumption`** | **0.40** | Косвенное предположение системы без прямых упоминаний |

### 3.2. Алгоритм распространения достоверности (Confidence Propagation)
1.  **Наследование от доказательств**: Достоверность `Fact` рассчитывается как максимальная достоверность среди всех связанных с ним объектов `Evidence`:
    $$Confidence_{Fact} = \max_{e \in Evidence}(Confidence_e)$$
2.  **Корректировка навыка**: Достоверность навыка `Skill` рассчитывается как средневзвешенное значение уверенности всех подтверждающих его фактов и проектов:
    $$Confidence_{Skill} = \alpha \times \max_{f \in Facts}(Confidence_f) + (1 - \alpha) \times \frac{\sum_{p \in Projects} Confidence_p}{|Projects|}$$
    где $\alpha = 0.7$ (вес фактов выше, чем простое упоминание технологии в файлах проекта).

## 4. Семантический Поиск и Сценарии RAG
Структурирование данных в граф связей дает колоссальные преимущества для построения систем RAG:
*   **Исключение галлюцинаций**: Любой сгенерированный ИИ ответ на техническом собеседовании или в тексте портфолио сопровождается цепочкой ссылок: `Утверждение -> Метрика -> Узел графа -> Ссылка на код (Evidence)`.
*   **Контекстный сбор**: При вопросе «Расскажи про интеграцию Dynamics NAV» RAG извлекает не просто случайный чанк текста резюме, а связку `[Project: Mediacube NAV Sync] -> [Fact: n8n ETL sync] -> [Metric: 90 min to 1 min] -> [Decision: Why SOAP] -> [Lesson: SOAP Idempotency]`.
