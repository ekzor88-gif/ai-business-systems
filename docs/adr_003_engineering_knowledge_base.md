# Architecture Decision Record (ADR-003): Редизайн слоя хранения инженерных знаний

*   **Статус**: Принято (Approved)
*   **Дата**: 2026-07-01
*   **Автор**: Principal Software Architect & Data Architect

---

## 1. Контекст и проблематика
Платформа **Portfolio Factory** использует локальный JSON-файл в качестве базы знаний (`knowledge.json`). Текущая реализация Context Manager успешно агрегирует данные из резюме, но плоская структура JSON имеет серьезные архитектурные ограничения при масштабировании.

С ростом объема данных (более 200 проектов, 500+ фактов, десятки репозиториев, видео, скриншоты, статьи) текущий подход приведет к спагетти-данным, дублированию информации и невозможности использования для точного контекстного RAG-поиска.

---

## 2. Анализ недостатков текущего knowledge.json

### Недостаток 1: Хранение `raw_resume_data` в семантическом слое
*   **Почему это проблема**: Сырой, неструктурированный текст из резюме лежит в одном файле с нормализованными данными. Это смешивает уровни абстракции.
*   **Последствия через год**: Избыточный рост файла, замедление парсинга, усложнение RAG-поиска (модели ИИ будут отвлекаться на дублирующий сырой текст).
*   **Решение**: Перенос сырых материалов на отдельный уровень хранения `storage/raw/`.
*   **Правила миграции**: Удалить `raw_resume_data` из `knowledge.json`. Все необходимые факты перенести в нормализованный граф.

### Недостаток 2: Проекты растворены внутри опыта работы (`work_experience`)
*   **Почему это проблема**: Проект не является самостоятельным объектом. Невозможно привязать проект к нескольким компаниям (например, субподряд) или репозиториям.
*   **Последствия через год**: Дублирование данных проектов при упоминании в разных периодах работы, невозможность построить сквозную аналитику по проектам.
*   **Решение**: Выделение сущности `Project` в самостоятельную вершину графа с уникальным ID. `Experience` ссылается на проекты через массив ID.
*   **Правила миграции**: Каждое место работы сканируется, из него выделяются проекты, создаются уникальные ID (например, `proj_mediacube_sync`), и они помещаются в массив `projects` на верхнем уровне.

### Недостаток 3: Смешивание технологий (`Technology`) и опыта их применения (`Skill`)
*   **Почему это проблема**: «Python» и «FastAPI» сейчас хранятся как навыки конкретного кандидата. Но сама технология имеет свои атрибуты (вендор, ссылка на документацию, категория), независимые от кандидата.
*   **Последствия через год**: Невозможность семантического RAG-анализа по технологиям и автоматического обновления документации по ним.
*   **Решение**: Разделение на сущность `Technology` (глобальный реестр технологий) и `Skill` (количественная и качественная оценка владения кандидата этой технологией).
*   **Правила миграции**: Создать плоский справочник `technologies` на верхнем уровне, связав его по ID со `skills` и `extracted_facts`.

### Недостаток 4: Размытые числовые метрики
*   **Почему это проблема**: Измеримые достижения (например, «сократил с 90 до 6 минут») зашиты в виде текста внутри описания факта. Их нельзя визуализировать на графиках или использовать для автоматического сравнения.
*   **Последствия через год**: Невозможность построить динамические инфографики и сравнивать эффективность инженера по годам.
*   **Решение**: Выделение сущности `Metric` с полями `before`, `after`, `unit` и `improvement_percent`.
*   **Правила миграции**: Написать парсер/LLM-инструкцию для выделения числовых показателей из описания фактов и переноса их в связанные объекты `Metric`.

### Недостаток 5: Отсутствие трассируемости и доказательств (`Evidence`)
*   **Почему это проблема**: Любое утверждение в резюме может казаться голословным без ссылки на первоисточник.
*   **Последствия через год**: Низкий уровень доверия к сгенерированному портфолио у работодателей.
*   **Решение**: Внедрение сущности `Evidence`, связывающей каждый факт или проект с коммитом, строкой кода, сертификатом или документом.
*   **Правила миграции**: Присвоить всем старым фактам дефолтное свидетельство `ev_cv_docx` (ссылка на оригинальный файл резюме) с уверенностью `0.5`.

## 3. Принятые решения

1.  **Создать трехуровневую архитектуру хранения (Storage Layers)**:
    *   `storage/raw/` — оригинальные неизмененные файлы (PDF, DOCX, README).
    *   `storage/normalized/` — структурированные, но независимые файлы (парсинг отдельных источников).
    *   `storage/knowledge/` — итоговый связанный семантический граф знаний (`knowledge.json`).
2.  **Перевести базу знаний на граф-ориентированную схему**:
    Каждая сущность (11 типов) хранится в плоских массивах в `knowledge.json` и ссылается на другие сущности через строковые ID в качестве ребер графа.
3.  **Внедрить оценку достоверности (Confidence Model)**:
    Установить веса достоверности источников (от `1.0` для исходного кода до `0.4` для предположений) и правила их распространения.
4.  **Сделать Уроки (Lessons Learned) и Решения (Engineering Decisions) первыми классами данных**:
    Каждое архитектурное решение и выученный урок должны храниться как самостоятельные объекты, чтобы в будущем питать RAG-систему подготовки к собеседованиям.

---

## 4. Последствия решения
*   **Плюсы**:
    *   Полная прослеживаемость данных (любое достижение подтверждается ссылкой на код).
    *   Отсутствие избыточности и дублирования данных.
    *   Идеальная подготовка контекста для RAG: LLM может за один запрос собрать связанную цепочку `[Проект] -> [Факт] -> [Метрика] -> [Код] -> [Урок]`.
*   **Минусы**:
    *   Усложняется логика первоначальной сборки графа в Context Manager.
    *   Требуется строгая валидация внешних ключей (проверка битых ссылок по ID внутри JSON).
